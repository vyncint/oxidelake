## Decisions recorded during implementation

- Operator parameter types (`Predicate`, `AggregateSpec`, …) live in `oxidelake_core::params`, not `oxidelake-compute`: the device crate's operator arguments need them and `oxidelake-compute` depends on `oxidelake-device`. `oxidelake-compute` re-exports them.
- The spill manager's device tier is abstracted behind `oxidelake_memory::DeviceResident` (bytes + copy-to-host), so `oxidelake-memory` never depends on a backend; the Arrow IPC spill codec lives in `oxidelake_memory::ipc` (storage reuses it) to keep the dependency direction.
- Spill accounting uses each batch's logical host size recorded at first host residency: batches decoded from IPC over-report `get_array_memory_size` because every column counts the shared message buffer.
- cudarc panics if a driver symbol is requested while `libcuda` is absent; the CUDA backend probes `cudarc::driver::sys::is_culib_present()` before any driver call, so a GPU-less machine gets `EngineError::Device`, never a panic.

- `Gpu*Exec` nodes carry the *planned* backend as their `EXPLAIN` tag but select the *real* backend at `execute()` from `local_backend()` (hardware detector, cached per process); any `Unsupported` from a GPU path falls back to the CPU reference for that batch.
- Device-side prefix scans (block counts, per-row join match counts) round-trip through the host in v1; the aggregate's group table is finalized on the host (sorted, `NULL` group last) so results match the CPU reference exactly. Device `SUM(Int64)` wraps on overflow where the CPU path errors — documented divergence.
- `GpuAggregateExec` concatenates all input partitions before aggregating (single output partition); `GpuHashJoinExec` collects the whole build side **once** and shares it across probe partitions (a lazily started `Shared` future, reset by `with_new_children`/`reset_state`). Both are v1 simplifications recorded for Phase 5 planning.
- **Correctness bug found and fixed on the first Metal machine (2026-09-01):** `GpuHashJoinExec` used to collect its build side once *per probe partition*. With a shared-state build child — `RepartitionExec` hands each row to exactly one consumer — every probe partition joined against a different fragment of the build side and matches were silently lost. It never showed before because the Linux box ran embedded mode with a CPU target (no rewrites) and Ballista's stage boundaries made the build side a re-executable shuffle read; the first embedded multi-partition GPU-target run (`--features metal`, M4 Pro) caught it. Regression test: `join_collects_repartitioned_build_side_once` (red on the old code, green now).
- **Third correctness bug, found on the first CUDA machine (2026-09-06, Tesla T4):** `oxide_ag_slot` in `aggregation.cu` let a thread that lost the CAS for a group-table slot compare the slot's key through a plain load after spinning on the state word. That load could observe the pre-publication key, so the loser probed on and inserted the same key in a second slot; every pass-2 lookup resolved to the first slot, and the host emitted the phantom as a duplicate group with `COUNT` 0 and `NULL` aggregates (`3|NULL|0|NULL|NULL` next to the real `3|489.0|40|…`). Deterministic on the T4 for the demo table (100 keys, 4000 rows) — the compute conformance suite's 10-key fixtures never hit it. Fix: the state and key are read through `volatile` loads with a fence between them that pairs with the publisher's fence; lookups in later launches need neither. Regression test at the device layer: `aggregate_matches_host_on_the_demo_distribution` (`#[ignore]`, needs a GPU), red on the old kernel and green on the fix on the same machine. Lesson, same as the Metal one: "compiles with `--features cuda`" is not a verification status; the row above says what ran.
- **Second correctness bug, found running the README's 1M-row quickstart against a real cluster (2026-09-01):** the aggregate lowering replaced the Final/Partial pair *and the exchange between them*, leaving `GpuAggregateExec` directly over a multi-partition scan. Embedded mode is fine (the exec collects every input partition itself), but Ballista cuts shuffle stages exactly at exchange nodes (`CoalescePartitionsExec` / `RepartitionExec` / `SortPreservingMergeExec`), so the distributed plan lost every scan partition but one — `SUM(v)` came back ~16× too small. Every earlier cluster test used files under DataFusion's 10 MiB `repartition_file_min_size`, so scans were never byte-range-split and the shape never existed. Fix: the rule now keeps one `CoalescePartitionsExec` under `GpuAggregateExec` whenever the source is multi-partition; `cluster_sql_matches_embedded_sql` now generates an 11 MiB file so the multi-partition shape is pinned in CI; verified by hand that the 1M-row cluster output is byte-identical to embedded.
- Metal v1 compares `Int64` only (no `double` on most Apple GPUs); `Float64` predicates return `Unsupported` and take the CPU path.

- Storage keeps no private format: `oxidelake-storage` owns Parquet writer properties, session pruning settings, Arrow IPC cache files and the object-store layer; pruning is *proven* by reading `row_groups_pruned_statistics` / `row_groups_pruned_bloom_filter` back from the executed plan rather than assumed.
- The io_uring store implements only the data path (`get_opts` ranged reads, `put_opts` overwrite writes) on its ring thread and delegates metadata operations to the wrapped `LocalFileSystem`, which is what makes the two stores behaviourally identical.

- DataFusion builds hash joins on the *left* input and may push a projection into the join; `GpuHashJoinExec` streams its left (probe) input and collects its right (build) input, so the rule swaps sides and re-expresses DataFusion's `left ++ right` order plus projection as an output projection — the rewritten node's schema is checked to be identical before it replaces the original.
- Under Ballista's session configuration DataFusion plans `SortMergeJoinExec`; the rule lowers it too (same inner-join semantics) and drops the `SortExec`s inserted for the merge.
- Final/Partial aggregate pairs are replaced as a unit by one `GpuAggregateExec` over the partial's input, keeping DataFusion's output field names via `with_output_schema`.
- Our codec wraps Ballista's (`OxidePhysicalCodec::new(BallistaPhysicalExtensionCodec)`): `Gpu*Exec` payloads carry a magic prefix, everything else is delegated, so shuffle nodes keep working.

- The dashboard renders a `DashboardModel` (telemetry snapshot + column profiles) through a pure `render(state, model, frame)`; the demo binary feeds a fixed fixture and repaints only on input/resize (no clock), which is what makes the PTY snapshots reproducible. Repaints are bracketed in DEC 2026 synchronized updates so termlens `wait_frame` never sees a torn frame.

- Phase 7: DataFusion 54's physical `ProjectionPushdown` folds expression projections into `DataSourceExec` itself, where no later rule can rewrite them — so vector-distance lowering runs as its own `VectorDistancePlacementRule` inserted **before** `ProjectionPushdown` (via `physical_optimizer_rules`), while every other lowering stays at the end of the pipeline where the exchanges and join orders it matches are final. The logical twin (`enable_leaf_expression_pushdown`) is disabled in the base session config for the same reason: small scans must not silently lose GPU placement that large (repartitioned) scans keep.
- The UDFs live in `oxidelake_compute::udf` and compute with the same reference arithmetic as the CPU kernel (`kernels::l2` / `kernels::cosine`), so a lowered and an un-lowered plan agree exactly. They are registered in four places: embedded sessions, cluster client sessions, the scheduler's session builder, and every executor's `BallistaFunctionRegistry`. `oxidelake-api` reaches them through `oxidelake_runtime::udf` (a re-export), keeping the crate's declared dependency direction (api → runtime).
- Embedded sessions wire their `TelemetryHub` into the placement rule (`HardwarePlacementRule::with_telemetry`), so every `Gpu*Exec` a session plans reports per-batch counters; `oxide tui --query` renders the executed plan, those counters (aggregated per operator name across partitions) and per-column profiles (min/max/nulls/quantiles via one aggregation query per table).
- Security + performance audit (2026-09-02, see [docs/audit-2026-09-02.md](docs/audit-2026-09-02.md)) — decisions taken:
  - The operator layer, not the backends, owns column plumbing: only the columns a kernel reads are uploaded; projected columns of device-ineligible types (`Utf8`, …) stay on the host and are gathered with Arrow `take` at the row ids the device compacted (a synthetic `__oxide_row` column travels with the sub-batch). A string column in the projection no longer sends the whole batch to the CPU path.
  - Backends declare what they support before anything is uploaded (`GpuBackend::supports_predicate` / `supports_hash_join` / `supports_aggregate`, default `true`; Metal says `false` for joins, aggregates and non-`Int64` predicates).
  - A hash join's build side is hashed once (`JoinBuild` → `kernels::JoinTable`, a flat row array grouped by key) and uploaded once per operator; probes gather only projected columns. Previously the table was rebuilt on the CPU and the build side re-uploaded for every probe batch.
  - Column transfers are zero-copy where the transport allows: `ColumnBytes` holds Arrow `Buffer` slices, rebuilding moves the downloaded buffers, and Metal downloads alias the shared `MTLBuffer` through `Buffer::from_custom_allocation` (the `Arc<MetalSharedBuffer>` keeps it alive). One memcpy into shared memory per upload remains (Arrow allocations are not page-aligned).
  - Metal caches compute pipeline states per kernel, encodes each phase into one command buffer (two waits per filter batch instead of one per kernel), pools four command queues for every stream (one queue per partition per query would exhaust the device's limit), and surfaces command-buffer errors instead of reading stale output.
  - `TelemetryHub` registers one entry per exec instance (shared by partitions) and keeps at most `MAX_OPERATORS = 4096`, evicting the oldest, so a long-lived session cannot grow without bound; `clear_operators` exists for dashboards.
  - GPU-targeted sessions run with `batch_size = 65 536` (`GPU_BATCH_SIZE`) to amortise the fixed per-dispatch cost; CPU-targeted sessions keep DataFusion's default.
  - `oxide gen-data` streams chunks into the Parquet writer (peak memory is one chunk + one row group, whatever `--rows` is); the `s` column is built from 13 static strings.
  - CUDA `aggregation.cu`: the slot-claim spin-wait reads through a `volatile` pointer (a hoisted load would loop forever); documented dependence on independent thread scheduling (sm_70+). CUDA `CudaFunction`s are cached per entry point. Both compile-verified only — no CUDA machine has run this code.
  - `GpuFilterExec` predicates are capped at 64 comparison leaves (`MAX_PREDICATE_LEAVES`) so a plan payload cannot drive the recursive evaluators arbitrarily deep; the dashboard quotes table identifiers like column identifiers.
  - `rust-version` is the lockfile's real floor (1.94.1 — Ballista's bundled AWS SDK crates), not the 1.88 the spec derived from direct dependencies; CI now checks it. `cargo deny` runs in CI with justified ignores for advisories in code paths OxideLake never reaches (`quick-xml` via `object_store`'s cloud backends) and for unmaintained compile-time-only crates.
- PyO3 bindings (`python` feature): **deferred.** A loadable module needs `crate-type = ["lib", "cdylib"]` on `oxidelake-api` — crate types cannot be feature-gated, so the extra cdylib artifact would burden every default build — plus `maturin` for packaging, and the spec excludes the feature from every gate, leaving CI unable to protect it. Recorded as the follow-up: a separate non-workspace `oxide-python` crate built with maturin against `oxidelake-api`, exposing `OxideSession::local`, `register_parquet`, `sql` → Arrow FFI (`arrow/ffi`) into `pyarrow`.
